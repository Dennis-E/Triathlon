# Implementation Plan: Choose Export Download Location

**Branch**: `057-export-download-location` | **Date**: 2026-10-14 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from [spec.md](./spec.md)

## Summary

Allow users to choose a destination for the PNG generated by the existing export preview.
At the existing Download action, use the browser's user-initiated save-location picker when
available; write the already-generated image to the chosen file and keep the current anchor
download path as the compatibility fallback. Treat user cancellation as a quiet, retryable
outcome and report genuine write failures. No export generation, tile coverage, or upload
behavior changes.

## Technical Context

**Language/Version**: Browser JavaScript in classic dashboard scripts

**Primary Dependencies**: Existing browser APIs, `src/dashboard-export.js`,
`src/export-utils.js`; no new package dependency

**Storage**: User-selected local PNG file only; no app-managed persistence

**Testing**: Jest 30 with Node environment; focused export-download orchestration coverage,
existing export utility and inline-script syntax tests; manual browser save-dialog check

**Target Platform**: Static browser app on modern browsers; save-location picker is
capability-/policy-dependent, with the current download behavior retained as fallback

**Project Type**: Static browser-first application

**Performance Goals**: Save action is initiated immediately from the user's click; no
additional export capture or image recomposition is required

**Constraints**: Picker invocation must remain within a user gesture; secure-context and
browser support restrictions apply; cancellation must not be mistaken for an error; export
image and personal activity data remain local; existing PNG content and suggested filenames
remain unchanged

**Scale/Scope**: One preview-modal download action shared by all export tiles and the existing
PNG generation path; no changes to export buttons, capture targets, or export composition

## Constitution Check

### Before Phase 0

- **I. Static Browser-First Delivery**: PASS — use built-in browser capability detection and
  the existing script; no build step or package is added.
- **II. Dual-Target Reusable Modules**: PASS — picker interaction is DOM/UI orchestration,
  appropriately kept in the existing classic-script export coordinator. Pure helper logic,
  if needed, stays in the existing CommonJS + browser-bridge export utility.
- **III. Narrowest-Scope Test-First Verification**: PASS — add focused tests for supported,
  unsupported, cancelled, failed, and retry flows; run the narrowest export and syntax suites.
- **IV. Faithful Locale-Aware Data Parsing**: PASS — imports and activity parsing are
  untouched.
- **V. Explicit Privacy & Network Boundaries**: PASS — the image is written locally and is
  not sent to a service; the ordinary app's existing network requests are unchanged.

No gate violations or unresolved technical clarifications were identified.

### After Phase 1

- **I–V**: PASS — the design adds a browser-mediated local file-save choice and preserves the
  static app, local-data boundary, existing export content and fallback. Validation is
  documented in [quickstart.md](./quickstart.md).
