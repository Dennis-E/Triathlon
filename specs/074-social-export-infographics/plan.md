# Implementation Plan: Social Export Infographics

**Branch**: `074-social-export-infographics` | **Date**: 2026-10-30 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification for a share-ready redesign of every currently exportable visualization, with family-specific rules for six named visualization families.

## Summary

Replace the current square, filter-heavy export composition with a deterministic social infographic renderer for every existing export target, including personal-best detail cards. The six detailed families receive dedicated presentation rules; all other current views use the same headline, visualization, context, branding, format, and preview/download contract while preserving their meaningful analysis. Reuse the existing DOM capture and local PNG download flow, and expand its pure layout helpers to generate square and portrait compositions from one captured data state. No analytics, import behavior, remote upload, bundler, or new runtime dependency is introduced.

## Technical Context

**Language/Version**: Browser JavaScript (classic scripts; Node.js CommonJS-compatible pure utilities)

**Primary Dependencies**: Existing html2canvas 1.4.1, Canvas 2D, Chart.js, and Leaflet; no new runtime dependency planned

**Storage**: None; export state and generated image remain in browser memory until dismissed or downloaded

**Testing**: Root Jest suite in Node; focused export, export-utils, heatmap, equipment, and scatter tests, plus browser verification for visual output

**Target Platform**: Static browser application, desktop-first authoring; exported images read at 360 px feed width

**Project Type**: Static web application with DOM-orchestration scripts and CommonJS/browser-bridged utilities

**Performance Goals**: No numeric latency target is specified. Rendering MUST wait for required resources and provide a clear failure state; it MUST not emit partial images.

**Constraints**: No bundler/build step or server upload. Fixed PNG sizes are 1080 × 1080 and 1080 × 1350. The same snapshot must drive preview and download. A heatmap must preserve the viewport chosen by pan/zoom; its 65% height target is subordinate to preserving geographic bounds without cropping or distortion.

**Scale/Scope**: Every current export action/target, including PB detail exports and non-specialized dashboard views; six named families receive additional domain-specific presentation rules.

**Structure Decision**: Extend existing export ownership rather than add a new subsystem. `index.html` owns the export controls; `dashboard-export.js` owns DOM capture, resource coordination, canvas composition, preview, and download; `export-utils.js` owns deterministic format/layout calculations and serializable metadata validation. Dashboard visualization modules expose narrow read-only export metadata only where current state cannot be derived reliably from the existing chart/view target. Keep the project's classic script load order intact. No external API contract is added; the user-facing contract is specified in `contracts/export-experience.md`.
